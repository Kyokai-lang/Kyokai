# Calculus Deviation Record

**Status:** maintained proof-abstraction record  
**Scope:** intentional differences between normative Kyokai surface semantics and public calculus artifacts

## 1. Rule

This file records only deliberate proof abstractions. It is not a place to preserve mistakes. When a calculus rule conflicts with the normative spec without a valid abstraction boundary, the calculus must be repaired and the invalid rule must not be retained as a deviation.

Discovered ambiguity, incompleteness, contradiction, unreviewed mismatch, and
open correspondence work belong in `findings-divergence.md`. Routing a finding
there does not turn it into an accepted abstraction or a resolved semantic rule.

Each row states the normative Kyokai rule, the calculus treatment, why the treatment is valid for the named theorem boundary, and what remains outside the claim.

## 2. Active Abstractions

| Subject | Normative Kyokai rule | `lambda_K-seq` treatment | Reason the abstraction is valid | Excluded or later obligation |
| --- | --- | --- | --- | --- |
| Anonymous borrow scopes | Ordinary `&[T]` and `&![T]` borrows use anonymous scope-bounded regions. Named regions appear only when an API relationship must be expressed. Surface `drop;` closes the current borrow scope. | Elaborated core introduces static region atoms such as `rho`, runtime maps them through `I` to fresh identities such as `r`, and region frames close explicitly when the elaborated extent ends. The core does not spell surface `drop;` as a separate term. | The proof needs names for region opening, non-escape, suspension nesting, and close. The names expose checker state without adding a source-level region argument. The region-frame end is the proof-facing close point for an explicit or compiler-selected scope extent. | Surface conformance must prove that anonymous borrow syntax and surface `drop;` elaborate to the accepted lexical extent without ending an outer scope early or silently extending access. |
| Borrow leases | Surface programs do not write lease identities. | Elaborated borrow and reborrow nodes carry static lease atoms such as `b`; runtime maps them through `I` to fresh identities such as `beta`. | The proof needs stable identities for copied access tokens and suspension edges. The atoms are checker evidence, not new source syntax. | Compiler dumps and diagnostics must explain inserted borrows without requiring programmers to write lease atoms. |
| Named consuming operations | Cleanup is an ordinary named consuming function, method, or typeclass operation. Kyokai never synthesizes structural destruction for user records or unions. | `consume[op] x` abstracts one already-resolved named consuming operation with admitted declaration `Delta |- op admitted-consuming T -> Unit`. | The first theorem needs one small visible discharge step for abstract resources. The rule is keyed by a named declaration and has no type-structural fallback. | Rich function bodies, `Destroyable`, `Cleanable`, domain-specific result values, `defer`, and composite cleanup proofs belong to later layers. |
| Integer family | Kyokai exposes width-specific checked integer behavior. | The first core uses abstract `IntK` plus checked primitives. | Width-independent progress and ownership arguments do not need backend bit-width details. | Width tables, lowering, overflow conformance, and generated-C/C-toolchain UB closure remain backend obligations. |
| Resources and capabilities | Concrete APIs define resource, capability, authority, and failure contracts. | The first core uses abstract `Resource[k]`, `Capability[k]`, and consuming attenuation. | Abstract kinds are enough to state unique ownership and non-forgery. | OS authority, wrapper audits, allocator behavior, and FFI boundaries remain later obligations. |
| Sum data | Kyokai has richer nominal unions and records. | The first core includes minimal closed sums plus `Optional` and `Result` aliases. | Closed sums expose payload movement and branch joins without importing layout, partial moves, or full pattern syntax. | Records, rich unions, arrays, field paths, layout, and partial moves remain later extensions. |
| First-order call identity | Surface call evaluation evaluates and resolves the callee expression before arguments. | The first core uses checked first-order identity `call f[phi](args)` and materializes path certificate `pi` before argument evaluation. | The theorem isolates ownership transfer and checked call entry after callable resolution. It does not claim that surface callable lookup or callee-expression evaluation has already been proved. | Surface elaboration and conformance must prove that callable resolution and any callee-expression evaluation occur before core entry and preserve source order. |
| Mutable `Free` places | Safe Kyokai can mutably borrow addressable mutable `Free` places subject to ordinary exclusivity. | The first core borrows linear-owner slots only. | Mutation, invalidation, and reinitialization of unrestricted storage need a place-state extension. Treating `Free` storage as a linear owner would prove the wrong model. | A later place-state extension must model mutable `Free` storage and prove its source mapping. |
| First-core TPOE sources | Safe Kyokai classifies failed contracts, checked arithmetic, bounds failures, reached `unreachable`, and every other spec-named checked bug condition as TPOE. | The first core has `contract_false` and `checked_failure(op,args)`. A checked primitive can represent admitted arithmetic or bounds checks; other categories are routed to later surface or runtime layers. | The first progress theorem needs an intrinsic defined-failure state and enough checked operations to test the boundary without importing every runtime feature. | Later layers and surface mapping must cover the full normative TPOE taxonomy without collapsing panic or runtime-fatal into TPOE. |
| Lean spot artifact | A mechanized claim must name its exact checked theorem and assumptions. | `lean/KyokaiCalculusSpot.lean` uses simplified datatypes for narrow representation theorems. | The artifact is intentionally a local model check and is labeled narrowly. | It does not mechanically prove correspondence to the prose calculus, L1-L40, Theorem P, Theorem Q, compiler correctness, or whole-language soundness. The paper proof for L1-L40, Theorem P, and Theorem Q is maintained separately in `theorem-assembly.md`. |
